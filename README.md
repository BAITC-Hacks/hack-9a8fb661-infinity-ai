# Infinity AI — Agentic AI для прогноза выработки ВЭС

HackAlem AI 2026, трек «Энергетика». Команда Infinity AI.

Система сама выполняет полный цикл прогноза почасовой выработки ветроэлектростанции на 24–48 часов:
получает архивный прогноз погоды на момент выпуска → готовит признаки → (пере)обучает модель →
строит почасовой прогноз → анализирует результат → пересчитывает при обновлении входных данных.
Процесс воспроизводится «как в прошлом»: выпуски 31.01, 01.02, … 27.02.2026.

## Главное правило: никакой утечки будущего
Погода берётся из **Open-Meteo Previous Model Runs API** — только переменные `*_previous_day1/2`,
то есть значения из прогонов метеомодели, сделанных за 1–2 суток до целевого часа.
Для выпуска D (00:00 UTC) час +h ≤ 24 берётся из прогона за сутки, +h ≤ 48 — за двое суток:
оба прогона выпущены не позже D. «Текущие» (близкие к факту) переменные не запрашиваются вообще.
Обучение идёт на том же типе данных (архивные прогнозы за прошлое), модель обучается только на
фактах строго раньше момента выпуска. Проверка вшита в агент (`all_runs_before_issue`).

## Объект: ВЭС «Нурлы» (паспорт)
Источник: [Samruk-Green Energy, проект ВЭС 5 МВт](https://samruk-green.kz/index.php/ru/projects/1047-20210219-133650);
в системе — таблица `wind_objects`.

| Параметр | Значение |
|---|---|
| Станция | ВЭС 5 МВт, п. Нурлы, Енбекшиказахский район, Алматинская область |
| Оператор | ТОО «Samruk-Green Energy» |
| Ввод в эксплуатацию | 20 июля 2020 (строительство март–ноябрь 2018) |
| Плановая годовая выработка | около 16 млн кВт·ч |
| Турбины | 2 × Goldwind GW109/2500 (XINJIANG GOLDWIND Science & Technology), класс IEC IIA/IIIA |
| Мощность одной турбины | 2,5 МВт |
| Ротор | 3 лопасти, диаметр 109 м; лопасти — стеклопластик (Sinoma) |
| Башня | трубчатая коническая стальная, 80 м |
| Стартовая / номинальная / максимальная скорость ветра | 3 / 10,3 / 25 м/с |
| Координаты | T1: 43.645139, 78.535611 · T2: 43.643194, 78.538833 |

Как паспорт используется в системе: номинал 2,5 МВт переводит нормализованную мощность в МВт·ч;
высота ступицы 80 м обосновывает ветер на 100 м из метеомодели (ближайший уровень к ступице);
диапазон 3–25 м/с — ориентир для кривой мощности (нижняя граница в модели 1,5 м/с, потому что
прогнозный ветер занижен относительно измеренного на гондоле; отсечка 25 м/с совпадает с паспортом);
данные о пропусках (`wind_actuals_gaps`) — 245 пропусков, самый длинный 999 ч у T1 (май–июнь 2024).

## Архитектура
```
React UI (Vite, TS)  ──/api──►  FastAPI  ──►  ForecastAgent (цикл + политика пересчёта)
                                   │              ├─ fetch_forecast   Open-Meteo previous runs (+кеш data/cache)
                                   │              ├─ prepare_features плотность воздуха, v_eq, направление, порывы
                                   │              ├─ train_model      кривая мощности + бустинг остатков
                                   │              ├─ predict          48 ч × {T1, T2, станция}
                                   │              ├─ analyze          sanity-check, сравнение с прошлым выпуском
                                   │              ├─ evaluate         MAE/RMSE/skill к персистентности
                                   │              ├─ replan           пересчёт / переобучение по правилам
                                   │              └─ report           сводка LLM (OpenAI / vLLM на NVIDIA / mock)
                                   ├─ Chat-агент: LLM сам вызывает инструменты (function calling), SSE-поток
                                   └─ Store: ClickHouse (основное) | SQLite (запасное)
```
Политика перепланирования: новый прогон погоды (изменилась сигнатура) → пересчёт; разница ветра с
прошлым выпуском > 1.5 м/с → пометка ревизии; пропуск факта > 3 ч → пониженная достоверность;
MAE выпуска > 2× среднего → переобучение; ≥ 7 суток новых фактов → переобучение. Каждое действие
и его причина пишутся в журнал агента и видны в UI.

Модель: эмпирическая кривая мощности (медианы по бинам 0.25 м/с от прогнозного `v_eq` с поправкой
на плотность воздуха, монотонность через изотоническую регрессию) + `HistGradientBoostingRegressor`
на остатках (направление, порывы, сезон, час суток, горизонт). Отдельно для T1 и T2, станция = среднее.

## Агент: цикл, уведомления, диалог, база знаний
- **Цикл агента** (страница «Агент»): для каждого выпуска — получение погоды → подготовка данных
  (с учётом пропусков `wind_actuals_gaps`) → обучение по политике → прогноз → анализ → оценка →
  перепланирование → отчёт. Каждый шаг с причиной пишется в `agent_log` и показывается в UI.
- **Уведомления** (`/api/alerts`): резкие изменения выработки по ΔP̂ₕ = P̂ₕ₊₁ − P̂ₕ (порог 15 % Pном за час,
  30 % за 3 ч, задаётся под оператора), штиль, риск остановки по ветру (> 22 м/с), обледенение (< −10 °C),
  пониженная достоверность, решения агента. Для окна события проверяется расхождение с прошлым выпуском
  («сценарии заметно расходятся»). Пример: «Днём ожидается снижение мощности на 1,9 МВт (38 % Pном).
  Наиболее вероятное окно — 17:00–20:00. В этом интервале сценарии заметно расходятся с прошлым выпуском».
- **Диалог** (`/api/agent`, SSE): LLM сама выбирает инструменты — `get_forecast`, `get_alerts`,
  `get_metrics`, `get_agent_log`, `search_knowledge`, `run_forecast`. Ответ на русском или казахском.
  Провайдеры: vLLM (Qwen3.8-27B на NVIDIA H200) → OpenAI → правила (mock) с автоматическим переходом.
- **База знаний** (`python -m app.cli train-embeddings`): эмбеддинги обучаются на корпусе проекта
  (паспорт станции, методика, данные, метрики, README): TF-IDF по символьным n-граммам + SVD (LSA),
  индекс в ClickHouse (`knowledge_chunks`, `cosineDistance`) и в памяти. Никаких внешних сервисов.
- **Машина времени**: режим «Доступно тогда / Факт для оценки» и паспорт выпуска (`/api/passport`):
  момент выпуска, до какого часа был факт, окно публикации прогонов погоды, контрольная сумма входа,
  версия модели, отличие от прошлого выпуска.

## Интерфейс
Страницы: **Прогноз** (фильтры, полоса ключевых чисел, график/таблица с погодой и предыдущими
выпусками, уведомления агента), **Карта и 3D** (спутник, турбины, 3D-сцена площадки с ветром),
**Аналитика** (точность, кривая мощности, качество данных, тестовый период), **Агент**
(цикл агента и диалог). Русский/казахский, светлая/тёмная тема. Dev-сервер: `npm run dev` → :5180.

## Запуск
Нужно: Python 3.12, Node.js 20+, git. ClickHouse, GPU и ключи **не нужны**: по умолчанию — SQLite,
погода из кеша `data/cache`, агент отвечает по правилам на реальных данных. Проверено на чистой копии.

### Вариант 1 — локально (≈ 3 минуты)
```bash
git clone https://github.com/BAITC-Hacks/hack-9a8fb661-infinity-ai.git   # или: git pull origin main
cd hack-9a8fb661-infinity-ai
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements.txt
cp .env.example .env                       # SQLite, офлайн-погода, вход expert / infinity-demo

cd backend
python -m app.cli backtest                 # ~1 мин: 58 выпусков (январь — бэктест, 31.01–27.02 — тест)
python -m app.cli train-embeddings         # база знаний агента (эмбеддинги)
uvicorn app.main:app --port 8010           # API; оставить запущенным
```
Во втором терминале:
```bash
cd hack-9a8fb661-infinity-ai/frontend
npm ci
npm run dev                                # http://localhost:5180  (вход: expert / infinity-demo)
```
Проверка: `cd backend && pytest -q` — 23 теста.

### Вариант 2 — Docker (одна команда, с ClickHouse)
```bash
docker compose up --build                  # UI: http://localhost:3000 (expert / infinity-demo)
```
При первом старте бэкенд сам прогоняет бэктест и обучает базу знаний.

### По желанию
- **Живая LLM:** в `.env` — `USE_MOCK_LLM=false` и `OPENAI_API_KEY=sk-…` (или `LLM_BASE_URL` для
  своей модели на vLLM, см. `gpu/README.md`). Без этого агент работает по правилам.
- **ClickHouse вместо SQLite:** `docker compose up -d clickhouse`, в `.env` — `DB_BACKEND=clickhouse`
  и пароль `CLICKHOUSE_PASSWORD`. Таблицы `wind_objects`, `wind_actuals`, `wind_actuals_gaps` создаются
  и заполняются при старте.
- **Свежая погода из сети:** `WEATHER_OFFLINE=false` (иначе только кеш из репозитория).
- **Показ команде в локальной сети:** `cd frontend && npm run serve:lan` → `http://<IP>:5180`
  (в Wi-Fi хакатона может мешать изоляция клиентов).

## Вход и безопасность
Интерфейс и API закрыты входом: логин/пароль из `.env` (`APP_LOGIN`, `APP_PASSWORD`), сессия —
подписанная HMAC-SHA256 cookie (HttpOnly, SameSite=Strict, 12 ч). Защита от перебора: 5 попыток
в минуту с IP. Заголовки `X-Frame-Options: DENY`, `nosniff`. Документация API скрыта при включённом входе.
**Доступ для команды в локальной сети:** `cd frontend && npm run serve:lan` — наружу открыт только порт 5180
(собранная минифицированная версия без исходников и source maps); API на 127.0.0.1:8010 доступен только через прокси и только после входа.
**Для проверки экспертами:** в `.env.example` и `docker-compose.yml` — `expert` / `infinity-demo`.
Пустой `APP_PASSWORD` отключает вход (локальная разработка, тесты). Пароль ClickHouse — только в `.env`.

## Проверка основного сценария
1. Открыть UI → выбрать выпуск `2026-01-31` → график прогноза на 48 ч, KPI, вывод агента.
2. Вкладка «Журнал агента» — шаги цикла с причинами решений (например, 25.02: «ветер в новом прогоне изменился на 2.4 м/с»).
3. Вкладка «Бэктест · январь» — MAE/RMSE/skill по горизонтам и по дням.
4. Вкладка «Тестовый период» — все февральские выпуски, скачивание `forecasts.csv`.
5. «Запустить агента» — повторный расчёт выбранного выпуска; «Спросить агента» — диалог с вызовом инструментов.

CLI: `python -m app.cli forecast 2026-02-10 --force`. Готовые результаты лежат в `outputs/`.

## Тесты
```bash
cd backend && pytest -q        # 20 тестов, без сети и ключей (SQLite + кеш погоды)
```
Проверяют: отсутствие утечки будущего (все прогоны погоды выпущены до момента прогноза,
модель не обучена на данных позже выпуска), UTC-конвертацию и флаг простоя, монотонность
кривой мощности, метрики, API (валидация входа, агентный цикл, пропуск пересчёта без
изменений, SSE-диалог в mock-режиме), справочник объектов.

## Проверка без API-ключей
`USE_MOCK_LLM=true` (по умолчанию). Прогноз от LLM не зависит; сводки и ответы чата строятся
правилами по тем же инструментам агента на реальных данных (понимает опечатки, «завтра/вчера», казахский). Погода берётся из `data/cache` (в Docker
`WEATHER_OFFLINE=true`), поэтому сеть тоже не нужна.

## Вклад команды: модель дата-инженера (`contrib/wind_hackathon_handoff/`)
Отдельный пакет коллеги по команде: прогноз с 10-минутной детализацией (288 точек на 48 ч) и
часовыми агрегатами, физическая кривая по паспорту + residual `HistGradientBoostingRegressor`,
обучение только по полным часам (6 валидных 10-минуток), CLI `train / predict / replay`, DDL таблиц
`wind_objects`, `wind_actuals`, `wind_actuals_gaps`, `wind_weather_forecasts`, `wind_power_forecasts`.
Вторая версия пакета добавляет загрузчик архивных прогнозов погоды (Open-Meteo, опционально NOAA GFS через `eccodes`),
агентный workflow, миграцию схемы `wind_hackathon_upgrade.sql`.
Тесты: `cd contrib/wind_hackathon_handoff && python -m unittest discover -s backend/tests -t .` (18 тестов).
Основной сервис (`backend/`) использует те же таблицы данных; модель пакета — альтернативный
вариант с 10-минутной детализацией. `backend/app/config.py` пакета взят из инфраструктуры проекта
KEGOC (переиспользование конфигурации, не решения задачи). Пароли — только в `.env.wind` (не в git).

## Известные ограничения
- Архив Open-Meteo previous runs доступен с 16.02.2024 — обучение на 2024-02…2026-01.
- Обе турбины попадают в одну ячейку сетки метеомодели — погодный ряд общий.
- Время в CSV интерпретируется как UTC+5 (подтверждено корреляцией с погодой; скачка в марте 2024 нет).
- Mock-LLM даёт шаблонные тексты; содержательные выводы — при `OPENAI_API_KEY` или `LLM_BASE_URL`.
