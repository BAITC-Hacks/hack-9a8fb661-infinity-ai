# Задание для Codex: развернуть модель прогноза двух турбин Нурлы

Ты работаешь на компьютере получателя комплекта `wind_hackathon_handoff.zip`.
Нужно развернуть и проверить переданную модель для хакатона HackAlemAI, подключить
её к ClickHouse и довести до реального обучения/прогноза по мере готовности погоды.
Сначала прочитай `README.md` и `docs/WIND_HACKATHON.md` из архива. Работай из корня
распакованного `wind_hackathon_handoff`, сохрани структуру Python-пакетов.
Не требуй весь исходный репозиторий KEGOC: нужные модули уже включены.

## Постановка и принятые решения

- Два исходных CSV — две турбины одной ВЭС Нурлы. Каждую моделируем отдельно.
- Факт: 11.03.2023–31.01.2026, преимущественно каждые 10 минут, с разрывами.
- Нужно последовательно воспроизвести прогнозы на исторические даты с 31 января
  до 28 февраля 2026 года. На каждый момент использовать только погодный выпуск,
  который был доступен тогда. Фактическая погода будущего запрещена во входах.
- Факта февраля нет. Нельзя подставлять его в признаки или объявлять известным.
- Горизонт 48 часов, 288 десятиминутных точек на турбину; сохраняем и 48 часовых
  агрегатов. Есть режим 24 часа. Для оценки хакатона основная детализация — час.
- Рабочие допущения уже приняты: время всего датасета — фиксированный UTC+5;
  `power_normalized = P / 2.5 МВт`; значение мощности представляет интервал,
  начинающийся с временной метки. Допущения описаны, повторно их согласовывать
  для запуска не нужно. Не выдавай их за подтверждённые свойства исходника.
- Паспортные ориентиры: две турбины по 2,5 МВт, башня 80 м, ротор 109 м,
  Goldwind GW109/2500, скорости 3 / 10,3 / 25 м/с.
- При среднем ветре <3 м/с в CSV встречается положительная мощность. Эти строки
  не удалять и не обнулять. Паспортная кривая — базовая оценка, ML-поправка
  может поднять итог выше нуля. Конечный CF ограничивается диапазоном 0–1.
- Нули и пропуски различаются. Длинные пропуски факта не интерполировать.
  Для обучения используются 10-минутные точки только из полных часов с 6
  валидными значениями мощности. Код уже реализует это правило.

## Подключение и данные

ClickHouse работает в Docker у коллеги:
- HTTP: `http://<IP-хоста-ClickHouse>:8123`, native: `<IP-хоста-ClickHouse>:9000`;
- база `wind`;
- выданные логин/пароль уже находятся в `.env.wind` в корне архива;
- runner автоматически загружает этот файл; переменные среды имеют приоритет.

Проверь доступность из этой машины. Если работаешь непосредственно на Mac
с опубликованными Docker-портами, `localhost:8123` может быть правильнее.
Подключение на машине автора не установилось, поэтому состояние реальной БД
не проверено и никаких удалённых записей автор не делал. Не выводи пароль в отчёт.

Файлы:
- `db/clickhouse/wind_hackathon.sql` — актуальный DDL, четыре таблицы и VIEW.
- `db/clickhouse/wind_objects_seed.sql` — INSERT справочника.
- `data/wind_objects.csv` — тот же справочник альтернативным форматом.
- `data/wind_actuals.csv` — готовый объединённый факт, заголовок:
  `object_id,timestamp,avg_wind,avg_tmp,power_normalized`.
- `data/source/turbine_1.csv`, `turbine_2.csv` — оригиналы для сверки.
- `data/wind_actuals_gaps.csv` — полный перечень разрывов.

Координаты после пересчёта DMS:
- object_id=1: latitude=43.645138889, longitude=78.535611111;
- object_id=2: latitude=43.643194444, longitude=78.538833333.

Времена в ClickHouse: `DateTime64(3, 'Etc/GMT-5')` — это именно UTC+5.
Никакого дополнительного сдвига +5 к уже локальным меткам CSV делать не нужно.
Связь таблиц: `wind_actuals.object_id = wind_objects.object_id`.
`ID` исходной строки CSV в объединённом факте не используется.

## Что уже написано

- `backend/app/forecasting/wind_hackathon.py`: подготовка факта, проверка погоды,
  интерполяция, физическая кривая, обучение residual HistGradientBoostingRegressor,
  подбор веса на временной валидации, прогноз и агрегация.
- `backend/app/forecasting/wind_hackathon_io.py`: чтение ClickHouse, артефакт модели,
  защита от использования модели с cutoff позже виртуального origin,
  выбор погодного выпуска, запись результатов.
- `backend/scripts/run_wind_hackathon.py`: `train`, `predict`, `replay`.
- `backend/tests/test_wind_hackathon.py`: 10 тестов без реальной БД.
- `requirements.txt`: минимальные зависимости для отдельного запуска.

Модель не использует TimesFM и не зависит от свежей февральской генерации.
Обучается на архивных ПРОГНОЗАХ погоды и соответствующей фактической мощности.
Измеренные `avg_wind`/`avg_tmp` CSV не выдаются за будущие погодные признаки.
Результат сохраняется в `wind_power_forecasts`, два `period_type`: `10min` и `hour`.
Новый расчёт создаёт новый `run_id`; предыдущие версии сохраняются.

## Порядок работы

1. Создай Python-окружение, установи `requirements.txt`, выполни:
   `python -m unittest backend.tests.test_wind_hackathon -v`.
   Проверь `python -m backend.scripts.run_wind_hackathon --help`.

2. Проверь подключение и реальные `SHOW CREATE TABLE`/столбцы существующих таблиц.
   Коллега мог уже создать справочник и факты и импортировать данные.
   Не загружай всё второй раз без проверки. Сохрани существующие данные.
   `CREATE IF NOT EXISTS` не обновит старую структуру. Если справочник имеет `id`
   вместо `object_id`, сначала установи фактическую схему и зависимости, затем
   приведи контракт к ожидаемому без потери данных.

3. Создай отсутствующие таблицы по актуальному DDL. Справочник/факт заполни только
   если они ещё не заполнены. `loaded_at` и `updated_at` заполнит ClickHouse.
   После загрузки `SELECT ... FROM wind_actuals FINAL` должен дать:
   object_id=1 — 142360 записей, object_id=2 — 149499 записей.
   Если факт уже загружен, проверь диапазоны и число строк вместо повторного импорта.

4. Учти изменение выходной схемы: ранний DDL был почасовым с `target_hour`.
   Сейчас нужны `timestamp`, `period_type`, `power_mw`, `energy_mwh` и сортировочный
   ключ, включающий period_type. Если найдена старая таблица, используй описанный
   в README вариант сохранения её под свободным именем и создания новой таблицы.
   Не удаляй старые данные и не принимай совпадение имени за совпадение схемы.

5. Проверь `wind_weather_forecasts`. В комплекте НЕТ погодного архива и его
   автоматического загрузчика. Если таблица пуста, следующая необходимая работа —
   реализовать получение архивных выпусков по координатам и загрузку в эту таблицу.
   Сначала проверь пригодность источника, потом загружай большой период.

   Важно: начальное направление — Open-Meteo Single Runs, но его текущая
   документация называет часть раннего ECMWF архива `hindcasts`. Это может быть
   ретроспективный перерасчёт, а не реальный выпуск, доступный на историческую дату.
   Проверь происхождение архива и требования кейса. Не подменяй архив прогноза
   реанализом или фактической погодой ради успешного запуска. Если подходящего
   источника подтвердить нельзя, явно зафиксируй это препятствие.

   Храни `issued_at`, `available_at`, `valid_at` раздельно. Дата скачивания
   архива не является исторической датой публикации. Не теряй версии выпусков.
   `provider`/`weather_model` должны совпадать с настройками обучения.
   По умолчанию это `open-meteo`/`ecmwf_ifs`, но источник можно выбирать аргументами.
   Нужны прогнозы до cutoff для обучения и выпуски для всего февральского replay.
   Минимум: ветер 80 м или 100 м и температура 2 м на всей временной сетке,
   включая правую границу горизонта; дополнительные поля перечислены в DDL.

6. После появления погоды обучи модель и сначала выполни расчёт с `--dry-run`.
   Например, первый виртуальный origin — `2026-01-31T18:00:00+05:00`.
   Cutoff обучения не должен быть позже него: вечерние данные 31 января после
   18:00 не должны попадать в обучение первого запуска. 18:00 — рабочий пример,
   время запуска нужно зафиксировать в документации эксперимента.

```bash
python -m backend.scripts.run_wind_hackathon train --cutoff 2026-01-31T18:00:00+05:00 --artifact outputs/wind_forecast/model.joblib
python -m backend.scripts.run_wind_hackathon predict --artifact outputs/wind_forecast/model.joblib --origin 2026-01-31T18:00:00+05:00 --dry-run
python -m backend.scripts.run_wind_hackathon replay --artifact outputs/wind_forecast/model.joblib --origin 2026-01-31T18:00:00+05:00 --until 2026-02-28T18:00:00+05:00 --step-hours 24 --output outputs/wind_forecast/replay.jsonl
```

   Если `available_at` неизвестно, код требует явного допущения
   `--publication-lag-hours 8` при обучении. Не включай его незаметно и не называй
   доказательством исторической доступности. Сохрани допущение в отчёте.
   Уже существующий артефакт не перезаписывается: для нового обучения нужен новый путь.

7. Проверь результат: за 48 часов на два объекта — 576 строк `10min` и 96 строк
   `hour`, всего 672 строки одного запуска. Часовая энергия должна равняться
   сумме энергии шести десятиминутных интервалов; не суммируй мощность как энергию.
   Часовые CF/МВт — средние. Не смешивай run_id и period_type при анализе.
   Для февральской оценки фильтруй цели внутри `[2026-02-01, 2026-03-01)` по UTC+5.

8. После рабочего расчёта можно подключать загрузчик обновлений/агента/дашборд.
   Пересчёт прогноза = новый доступный погодный выпуск → проверка → подготовка →
   инференс фиксированной модели → сохранение новой версии. Это не автоматическое
   переобучение. Агентный цикл в текущем архиве не завершён, не выдавай обычный
   CLI replay за полностью реализованного Agentic AI.
