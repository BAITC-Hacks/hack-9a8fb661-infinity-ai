# Задание для Codex коллеги: запустить прогноз двух турбин

Работай в распакованном wind_hackathon_handoff. Архив самодостаточен: весь проект
KEGOC не нужен. Сначала прочитай README.md и docs/WIND_HACKATHON.md. Нужно проверить
схему ClickHouse, запустить реальный workflow и собрать результаты, не переписывая
уже готовые загрузчики и модель без найденной причины.

## Контекст и уже принятые решения

Две турбины ВЭС Нурлы рассматриваются как отдельные объекты. Факт заканчивается
31.01.2026, февраля нет. Прогнозы воспроизводятся ежедневно с 31.01.2026 18:00
по 28.02.2026 18:00 UTC+5, горизонт 48 часов. Выход — 10 минут и почасовые агрегаты.
Вся шкала времени фиксированная UTC+5, включая 2023 год. Мощность нормализована
как P / 2.5 МВт; метка означает начало интервала, значение считается его средней.
Эти допущения уже приняты пользователем, повторного согласования не нужно.

Координаты: object_id=1 — 43.645138889, 78.535611111;
object_id=2 — 43.643194444, 78.538833333. Широта затем долгота. Высота башни 80 м,
диаметр ротора 109 м, номинальная мощность 2.5 МВт. Модель Goldwind GW109/2500.
Физическая кривая с ориентирами 3 / 10.3 / 25 м/с плюс обученный остаток HGB.
При ветре <3 м/с нельзя удалять положительный факт или принудительно обнулять
конечный прогноз. Обучение — по полным часам из шести 10-минутных меток. Пропуски
не превращать в нули. Будущий фактический ветер/температуру не подставлять.
TimesFM и коррекции по свежим февральским фактам здесь нет.

## Подключение и схема

.env.wind в корне архива содержит выданные пользователем креды:
ClickHouse HTTP <IP-хоста-ClickHouse>:8123, база wind. На Mac с опубликованным Docker-портом
может понадобиться localhost:8123. Пароль не выводи в отчёт. Автор не имел сетевого
доступа к этой БД; реального обучения или удалённых INSERT при сборке не было.

Сначала проверь существующие таблицы и данные. Используй wind_hackathon.sql
для отсутствующих таблиц и wind_hackathon_upgrade.sql для добавления метаданных
в существующие. Ничего не удаляй. CREATE IF NOT EXISTS не обновляет структуру.
Если старый справочник имеет id, ожидаемый контракт кода — object_id; если ранняя
таблица прогноза содержит target_hour, инструкция описывает её сохранение под
другим именем перед созданием актуальной таблицы timestamp/period_type.

Справочник: db/clickhouse/wind_objects_seed.sql ИЛИ data/wind_objects.csv.
Факты: data/wind_actuals.csv, колонки object_id,timestamp,avg_wind,avg_tmp,power_normalized.
Не загружай повторно исходные CSV data/source/. Если факт уже загружен — проверь
диапазоны и число строк FINAL: 142360 для объекта 1, 149499 для объекта 2.
Все 245 разрывов отдельно перечислены в data/wind_actuals_gaps.csv.

## Что реализовано

- wind_hackathon.py: подготовка, погодные признаки, HGB, физический ориентир,
  подбор веса, версии модели, 10-минутный прогноз и агрегация.
- wind_hackathon_io.py: чтение/запись ClickHouse, обучение, артефакты, защита cutoff.
- wind_weather_archive.py: Open-Meteo Single Runs по lat/lon из wind_objects,
  фиксированная модель ecmwf_ifs, UTC run, скорость м/с, исходные JSON и SHA-256,
  повторы HTTP, выбор старого полного выпуска при неготовности свежего.
- wind_noaa_archive.py: дополнительный оригинальный архив NOAA GFS с выборкой
  диапазонов GRIB, извлечением точки, проверкой публикации Last-Modified.
- wind_hackathon_agent.py: автономный контроллер на правилах, без LLM; решения,
  анализ, сравнение версий, проверка до публикации, пропуск неизменившихся входов,
  восстановление частичной записи того же run_id.
- wind_hackathon_workflow.py: backfill, независимый предфевральский holdout,
  финальная тренировка, 29 origin, почасовые выгрузки и отчёт покрытия февраля.
- CLI: check/fetch-weather/train/predict/replay/agent/workflow/evaluate.
- Два файла тестов, включая полный синтетический workflow. Дашборда нет.

## Важное различие архивов

Пользователь предпочитает прямой Open-Meteo по координатам. Это подключено.
Но ранний IFS архив документация называет 49R1 hindcasts. Поэтому код требует
--allow-hindcast для исследовательского февральского эксперимента и сохраняет
метку hindcast_unverified. Не скрывай этот факт и не объявляй эксперимент
доказанным выполнением требования «прогноз был доступен на ту дату».
Для Open-Meteo отдельно принято available_at = initialisation + 8 часов.
Ссылки и объяснение — в подробном README.

Для строгого as-issued replay предусмотрен --source noaa-gfs. Это исходные
операционные GFS-файлы, доступность проверяется по Last-Modified и времени внутри
GRIB. Нужна дополнительная установка requirements-wind-noaa.txt. Источник требует
много трафика; проверь один выпуск перед большим backfill. Признаки — ветер на 100 м,
его направление и температура на 2 м; поля, которых нет, не придумываются.
Исходные срезы через 3 часа интерполируются почасово по u/v. Для другого источника
нужна отдельная обученная модель, автоматической подмены Open-Meteo на GFS нет.

## Порядок запуска

1. Создай venv, установи requirements.txt. Выполни оба набора unittest из README.
2. Проверь/подготовь схему и факт, запусти python -m backend.scripts.run_wind_hackathon check.
3. Проверь небольшой fetch-weather для выбранного источника. Обязательно читать
   issued_at/available_at/valid_at раздельно. Дата скачивания не дата публикации.
4. Запусти workflow по инструкции. Для начала ограничь историю октябрём 2025,
   затем при необходимости расширь. Open-Meteo до 14.03.2024 не покрывает историю;
   исходные факты 2023 с ним не будут использованы в погодной тренировке.
5. Workflow создаёт validation_model.joblib с ранним cutoff для независимой
   проверки, затем финальную model.joblib до 31.01.2026 18:00. Не переносить
   поздние факты в признаки ранних запусков. Модель не обучается на феврале.
6. Проверь итог workflow.json, holdout_metrics.json и запись wind_power_forecasts.
   Для 48 часов ожидается 19488 строк за 29 origin, 1344 уникальных февральских часа.
   Точность февраля можно посчитать только после появления факта через evaluate;
   до этого статус awaiting_actuals, а не выдуманные MAE/RMSE.
7. Проверь agent --watch с фиксированным origin и --cycles 3: одинаковые входы
   пропускаются; изменённая погода/версия модели создаёт новую версию. --refresh
   заново опрашивает источник даже для кешированного выпуска. При необходимости
   загрузить новые факты выполнить отдельное переобучение с новым cutoff.

Артефакты хранятся в выбранном outputs-каталоге. Повтор workflow использует
существующие артефакты; для новых настроек/исправленного обучения нужен новый
каталог. .env.wind автоматически читается, env имеет приоритет.

В итоговом отчёте укажи: фактическую доступность БД, источник и происхождение
погоды, использованный диапазон истории, независимые метрики до февраля,
число origin/часов, пути выгрузок и ограничения. Не называй успешные unit-тесты
доказательством качества на реальной ВЭС. Если инфраструктура не отвечает,
зафиксируй конкретную ошибку и завершённые проверки, не подменяй данные заглушками.
