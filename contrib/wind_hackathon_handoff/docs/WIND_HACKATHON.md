# Прогноз двух турбин Нурлы

Первая версия `nurly_weather_residual_v1` — отдельная модель по каждой турбине.
Исходный `vie_weather_adaptive_v2` не изменён. Заимствован подход: погодная модель
и физический ориентир, отдельно обучаемая адаптация объекта.

## Что реализовано

- Чтение справочника, исходного факта и архивных погодных выпусков из ClickHouse.
- Проверка 10-минутной сетки. Дубликаты после `FINAL` и неверная сетка — ошибка.
- Часы с менее чем шестью валидными значениями мощности исключаются из обучения
  и оценки. Никакой интерполяции длинных разрывов, заполнения факта нулями или
  удаления положительной мощности только из-за ветра <3 м/с.
- Физический ориентир: начало 3 м/с, номинальная скорость 10,3 м/с,
  верхняя рабочая скорость 25 м/с. Это приближённая кубическая кривая, а не
  полученная от изготовителя полная паспортная таблица.
- Градиентный бустинг обучается предсказывать остаток фактической нормализованной
  мощности относительно кривой. Итог: `clip(physical + weight * residual, 0, 1)`.
  Пороги ветра НЕ принудительно обнуляют конечный ML-прогноз. Вес поправки выбирается
  из 0…1 по часовой MAE на отложенном временном отрезке. Если выигрывает вес 0,
  используется физический ориентир; это видно в артефакте модели.
- Признаки: прогнозные ветер на 80 м (100 м — явно обозначенный запасной вариант),
  направление, температура, давление, порывы, осадки, ветер 10 м,
  дальность от инициализации погодного выпуска, время суток и сезон.
  Нельзя брать максимум ветра по всем высотам вместо ветра около турбины.
- Погода интерполируется с часа до 10 минут, направления — через sin/cos.
  Требуется полное покрытие обязательных полей до правой границы горизонта;
  через пропущенный час погоды не интерполируем. Необязательные поля могут быть NULL.
- Обучение на 10-минутных метках только внутри полных часов. Перекрывающиеся
  погодные выпуски не увеличивают суммарный вес одной фактической метки.
- Проверка по последним 30 дням до cutoff: обучающие цели строго раньше границы,
  проверочные запуски начинаются после неё. Подбор веса на этой проверке не является
  независимой оценкой качества: окончательный тест — скрытый февраль.
- MAE/RMSE считаются после такой же почасовой агрегации, как при выдаче результата,
  отдельно MAE первых и следующих 24 часов. MAPE у нулевой мощности не используем.
- Запуски на 24/48 часов: 144/288 десятиминутных точек на турбину плюс 24/48 часовых.
  МВт = CF × 2,5; МВт·ч за интервал = МВт × длительность интервала в часах.
- Выбор последнего полностью покрывающего горизонт выпуска, доступного к виртуальному
  времени. Неполный свежий выпуск заменяется более старым доступным; если подходящего
  нет, весь расчёт завершается ошибкой без публикации частичного результата.
- Команды `train`, `predict`, `replay`. Повторный запуск с новым погодным выпуском
  создаёт новую версию прогноза. Старые версии не стираются.

## Что нужно в ClickHouse

Применить `db/clickhouse/wind_hackathon.sql` в БД `wind` и загрузить справочник
из `db/clickhouse/wind_objects_seed.sql`. Сам runner DDL не выполняет.

Схема `wind_objects` и `wind_actuals` соответствует последним согласованным DDL:
ключ `object_id`, в факте поля `avg_wind`, `avg_tmp`, `power_normalized`.
Объединённый CSV загружается с явным списком этих полей и `timestamp`.

Выходная таблица обновлена после решения считать 10-минутки: `timestamp` вместо
старого `target_hour`, добавлены `period_type`, `power_mw`, `energy_mwh`.
`CREATE IF NOT EXISTS` не изменяет старую таблицу! Если уже создана ранняя
почасовая версия, до применения DDL сохраните её под другим свободным именем:

```sql
RENAME TABLE wind_power_forecasts TO wind_power_forecasts_legacy_hourly;
```

Затем выполните новый DDL. Эта ручная операция сохраняет предыдущие данные.
Если поля уже соответствуют новому DDL, переименование не требуется.

`wind_weather_forecasts` необходимо наполнить архивными ПРОГНОЗАМИ, не погодным
фактом. Загрузчик внешнего API и дашборд не входят в этот модуль модели.
Для обучения требуется история погодных выпусков до cutoff, для replay — выпуски
января/февраля. Пара `provider, weather_model` должна совпадать с аргументами CLI.
Минимум на каждом прогнозируемом часу: ветер 80 или 100 м и температура 2 м.
`issued_at` — инициализация, `available_at` — реальная публикация,
`valid_at` — время прогноза. `loaded_at` архива никогда не используется как время
публикации. Все значения скорости ветра должны быть в м/с.

Когда `available_at` неизвестно, по умолчанию runner останавливается.
`--publication-lag-hours 8` явно разрешает допущение «выпуск доступен через 8 часов»
для таких записей. Оно сохраняется в артефакте. Это не доказательство исторической
доступности, и его надо описать в сдаваемом решении.

Важная проверка источника: текущая документация Open-Meteo Single Runs называет
ранний ECMWF архив `IFS Cycle 49R1 hindcasts`. Нельзя автоматически считать любое
ретроспективное моделирование исходным прогнозом, реально опубликованным тогда.
До загрузки нужно подтвердить происхождение выбранных выпусков и соответствие
правилам хакатона. Фильтр по времени в коде не может доказать происхождение данных.
Источник: https://open-meteo.com/en/docs/single-runs-api

## Запуск у коллеги

Python 3.12+, из корня репозитория:

```bash
python -m venv .venv
# macOS/Linux:
source .venv/bin/activate
python -m pip install -r backend/requirements-wind.txt
python -m backend.scripts.run_wind_hackathon --help
```

Рядом с корнем проекта передайте локальный `.env.wind`: в нём уже записано выданное
подключение к БД `wind`, HTTP-порт 8123. Файл исключён из git; передать отдельно.
Пароль не встроен в код и не выводится runner-ом. Используются `WIND_CLICKHOUSE_URL`,
`WIND_CLICKHOUSE_DATABASE`, `WIND_CLICKHOUSE_USERNAME`, `WIND_CLICKHOUSE_PASSWORD`,
`WIND_CLICKHOUSE_TIMEOUT_SECONDS`. Переменные окружения имеют приоритет над файлом.
Другой файл можно указать перед командой: `--env-file /path/to/.env.wind`.
На Mac, где опубликован Docker-порт, при необходимости заменить URL на
`http://localhost:8123`. Адрес <IP-хоста-ClickHouse> требует доступности локальной сети.

После загрузки факта и архивных погодных прогнозов:

```bash
python -m backend.scripts.run_wind_hackathon train --cutoff 2026-01-31T18:00:00+05:00 --artifact outputs/wind_forecast/model.joblib
python -m backend.scripts.run_wind_hackathon predict --artifact outputs/wind_forecast/model.joblib --origin 2026-01-31T18:00:00+05:00 --dry-run
python -m backend.scripts.run_wind_hackathon replay --artifact outputs/wind_forecast/model.joblib --origin 2026-01-31T18:00:00+05:00 --until 2026-02-28T18:00:00+05:00 --step-hours 24 --output outputs/wind_forecast/replay.jsonl
```

Если допустили лаг публикации 8 часов, добавьте его при **обучении**; инференс
автоматически использует сохранённое допущение. Не менять его между этапами.
18:00 — пример времени ежедневного запуска, не требование организаторов.
cutoff — исключающая граница факта: при первом запуске 31 января в 18:00 нельзя
использовать данные вечера 31 января после 18:00. Для модели, обученной до 1 февраля
00:00, самый ранний допустимый origin — 1 февраля 00:00.

`--dry-run` читает ClickHouse, но не пишет прогноз. Без него результат вставляется
в ClickHouse. Каждый повторный расчёт имеет новый UUID. Артефакты не перезаписываются:
для нового обучения задайте другой путь. Загружать joblib только из доверенного
локального обучения и в той же версии sklearn. Запуски replay выполняются по очереди;
ошибка останавливает цикл, уже завершённые версии сохраняются. Дата `created_at`
реальная, `forecast_origin` виртуальная. Первое предсказываемое окно —
`[origin, origin + 10 минут)`. Для оценки февраля фильтровать время цели внутри
`[2026-02-01, 2026-03-01)` и выбрать правило учёта перекрывающихся горизонтов.

В запросах результатов фильтруйте `period_type = 'hour'` либо `'10min'` и конкретный
`run_id`; нельзя складывать разные запуски или обе детализации.

## Допущения и ограничения

- CF = мощность / 2,5 МВт. Нормализация организаторами не подтверждена.
- Весь CSV трактуется в фиксированном UTC+5, включая 2023 год. Метка — начало
  10-минутного интервала. Средние ветер и температура не объявляются мгновенными.
- Мощность из CSV принимается средней за интервал для расчёта энергии.
- 80 м — опубликованная высота башни; точная высота измерителя неизвестна.
  При отсутствии прогнозного ветра 80 м используется 100 м без скрытого пересчёта
  по произвольно выбранному коэффициенту шероховатости.
- Объект сопоставлен с ВЭС Нурлы по координатам. Характеристики:
  https://samruk-green.kz/index.php/ru/projects/1047-20210219-133650
  https://www.thewindpower.net/windfarm_en_30769_nurly.php
- Измеренные `avg_wind`, `avg_tmp` сейчас служат для проверки/исследования факта,
  но не подаются как будущие признаки. Прямой ML-остаток учится на прогнозном ветре
  и тем самым учитывает систематические ошибки погодных прогнозов.
- TimesFM и коррекция по свежей мощности не используются: февральский факт не дан.
- Интерполяция погоды не создаёт новых наблюдений с 10-минутным разрешением.
- Диаметр 109 м — справочная характеристика, не постоянный ML-признак.
- Модель не знает статусы ремонта/диспетчерских ограничений, которых в CSV нет.
- Это вычислительный модуль и последовательный replay, не завершённый Agentic AI:
  автоматическая загрузка API, наблюдение за новыми выпусками, API дашборда и агентная
  оркестрация ещё должны быть подключены к функциям `train`/`forecast`.

## Проверка без БД

```bash
python -m unittest backend.tests.test_wind_hackathon -v
```

Проверяются пропуски, дубликаты, UTC+5, отсечение будущей погоды, запасной выпуск,
неизвестное время публикации, круговая интерполяция направления, энергия,
отсутствие жёсткого обнуления по ветру и полный цикл обучения/сохранения/прогноза
двух объектов на синтетических данных. Это проверка реализации, не доказательство
точности на реальной ВЭС; реальное обучение требует ClickHouse и погодного архива.
