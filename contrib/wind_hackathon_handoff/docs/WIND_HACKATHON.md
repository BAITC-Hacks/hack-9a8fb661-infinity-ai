# Прогноз двух турбин Нурлы

Первая версия `nurly_weather_residual_v1` — отдельная модель по каждой турбине.
Исходный `vie_weather_adaptive_v2` не изменён. Заимствован подход: погодная модель
и физический ориентир, отдельно обучаемая адаптация объекта.

## Что реализовано

- Чтение справочника, исходного факта и архивных погодных выпусков из ClickHouse.
- Проверка 10-минутной сетки. Дубликаты после `FINAL` и неверная сетка — ошибка.
- Часы с менее чем шестью валидными значениями мощности исключаются из обучения
  и оценки. Никакой интерполяции длинных разрывов, заполнения факта нулями или
  удаления положительной мощности только из-за ветра <3 м/с.
- Физический ориентир: начало 3 м/с, номинальная скорость 10,3 м/с,
  верхняя рабочая скорость 25 м/с. Это приближённая кубическая кривая, а не
  полученная от изготовителя полная паспортная таблица.
- Градиентный бустинг обучается предсказывать остаток фактической нормализованной
  мощности относительно кривой. Итог: `clip(physical + weight * residual, 0, 1)`.
  Пороги ветра НЕ принудительно обнуляют конечный ML-прогноз. Вес поправки выбирается
  из 0…1 по часовой MAE на отложенном временном отрезке. Если выигрывает вес 0,
  используется физический ориентир; это видно в артефакте модели.
- Признаки: прогнозные ветер на 80 м (100 м — явно обозначенный запасной вариант),
  направление, температура, давление, порывы, осадки, ветер 10 м,
  дальность от инициализации погодного выпуска, время суток и сезон.
  Нельзя брать максимум ветра по всем высотам вместо ветра около турбины.
- Погода интерполируется с часа до 10 минут, направления — через sin/cos.
  Требуется полное покрытие обязательных полей до правой границы горизонта;
  через пропущенный час погоды не интерполируем. Необязательные поля могут быть NULL.
- Обучение на 10-минутных метках только внутри полных часов. Перекрывающиеся
  погодные выпуски не увеличивают суммарный вес одной фактической метки.
- Проверка по последним 30 дням до cutoff: обучающие цели строго раньше границы,
  проверочные запуски начинаются после неё. Подбор веса на этой проверке не является
  независимой оценкой качества: окончательный тест — скрытый февраль.
- MAE/RMSE считаются после такой же почасовой агрегации, как при выдаче результата,
  отдельно MAE первых и следующих 24 часов. MAPE у нулевой мощности не используем.
- Запуски на 24/48 часов: 144/288 десятиминутных точек на турбину плюс 24/48 часовых.
  МВт = CF × 2,5; МВт·ч за интервал = МВт × длительность интервала в часах.
- Выбор последнего полностью покрывающего горизонт выпуска, доступного к виртуальному
  времени. Неполный свежий выпуск заменяется более старым доступным; если подходящего
  нет, весь расчёт завершается ошибкой без публикации частичного результата.
- Команды `check`, `fetch-weather`, `train`, `predict`, `replay`, `agent`, `workflow`,
  `evaluate`. Автоматический цикл получает погоду, выбирает доступный выпуск,
  проверяет покрытие, рассчитывает, анализирует и публикует результат.
- Источники: Open-Meteo Single Runs напрямую по координатам из `wind_objects`;
  дополнительно оригинальные архивные GRIB NOAA GFS для строгого as-issued replay.
- Хеш входов предотвращает повторную публикацию неизменившегося расчёта. Изменение
  погоды или версии модели создаёт новый `run_id`. Решения пишутся в JSONL.
- `workflow` автоматически готовит погоду, выполняет независимую проверку за 30 дней
  перед тестом, затем обучает финальную модель и воспроизводит весь февраль.
  Почасовой экспорт содержит все origin и отдельно последний прогноз каждого часа.

## Что нужно в ClickHouse

Применить `db/clickhouse/wind_hackathon.sql` в БД `wind` и загрузить справочник
из `db/clickhouse/wind_objects_seed.sql`. Сам runner DDL не выполняет.

Схема `wind_objects` и `wind_actuals` соответствует последним согласованным DDL:
ключ `object_id`, в факте поля `avg_wind`, `avg_tmp`, `power_normalized`.
Объединённый CSV загружается с явным списком этих полей и `timestamp`.

Выходная таблица обновлена после решения считать 10-минутки: `timestamp` вместо
старого `target_hour`, добавлены `period_type`, `power_mw`, `energy_mwh`.
`CREATE IF NOT EXISTS` не изменяет старую таблицу! Если уже создана ранняя
почасовая версия, до применения DDL сохраните её под другим свободным именем:

```sql
RENAME TABLE wind_power_forecasts TO wind_power_forecasts_legacy_hourly;
```

Затем выполните новый DDL. Эта ручная операция сохраняет предыдущие данные.
Если поля уже соответствуют новому DDL, переименование не требуется.

`wind_weather_forecasts` наполняется загрузчиком архивных ПРОГНОЗОВ. Дашборд в
комплект не входит. Для уже существующих таблиц дополнительно выполнить
`db/clickhouse/wind_hackathon_upgrade.sql`: это добавление полей происхождения
погоды, координат ячейки и хеша входов; строки и старые столбцы сохраняются.
Для обучения требуется история погодных выпусков до cutoff, для replay — выпуски
января/февраля. Пара `provider, weather_model` должна совпадать с аргументами CLI.
Минимум на каждом прогнозируемом часу: ветер 80 или 100 м и температура 2 м.
`issued_at` — инициализация, `available_at` — реальная публикация,
`valid_at` — время прогноза. `loaded_at` архива никогда не используется как время
публикации. Все значения скорости ветра должны быть в м/с.

Когда `available_at` неизвестно, по умолчанию runner останавливается.
`--publication-lag-hours 8` явно разрешает допущение «выпуск доступен через 8 часов»
для таких записей. Оно сохраняется в артефакте. Это не доказательство исторической
доступности, и его надо описать в сдаваемом решении.

### Open-Meteo и историческая доступность

Запрос идёт в `https://single-runs-api.open-meteo.com/v1/forecast` с массивами
`latitude`, `longitude` из справочника, фиксированной моделью `ecmwf_ifs`,
`run` в UTC и `wind_speed_unit=ms`. Обычные Archive/Reanalysis и бесшовный
Historical Forecast API не используются. Ответы кешируются вместе с URL,
параметрами, SHA-256, временем скачивания и фактическими координатами ячейки.
Два близких объекта могут иметь одну погодную ячейку — реальный запрос это подтвердил.
Поправка к мощности обучается отдельно для каждого объекта.

У источника есть существенная оговорка: документация называет ранние выпуски IFS
до обновления 12.05.2026 архивом `49R1 hindcasts`. Наличие параметра `run` само
по себе не доказывает, что эти расчёты были опубликованы в феврале. Поэтому
исторический эксперимент на Open-Meteo требует явного `--allow-hindcast`.
Строки помечаются `archive_kind=hindcast_unverified`, метка переносится в прогноз
и отчёт. Такой эксперимент нельзя объявлять доказанным выполнением требования
«доступно на тот момент». Флаг не заменяет подтверждение источника организаторами.

Для Open-Meteo `available_at = issued_at + 8 часов` — отдельное документированное
допущение о задержке публикации. Время скачивания не используется как историческое
время доступности. Выбирается последний допустимый цикл 00/06/12/18 UTC;
если он не покрывает горизонт, проверяются до трёх предыдущих циклов.
Источник: https://open-meteo.com/en/docs/single-runs-api

### Строгая альтернатива: NOAA GFS

`--source noaa-gfs` читает исходные операционные файлы из публичного архива
`noaa-gfs-bdp-pds`, а не последующий hindcast. Дата публикации берётся из
`Last-Modified` оригинального GRIB-объекта; берётся максимум по всем нужным файлам.
Если объект перепубликовали позже виртуального origin, он не допускается.
GRIB-инициализация и время прогноза сверяются с запросом. Диапазоны байтов и
контрольные суммы проверяются. AWS-аккаунт не нужен.

Берём компоненты ветра на 100 м и температуру 2 м, извлекаем ближайшую к каждой
турбине точку через ecCodes. В этом варианте давление/порывы/осадки отсутствуют,
модель обучается только на доступных признаках. Для ограничения трафика исходные
срезы берутся каждые 3 часа до +72 часов; почасовой ветер восстанавливается через
линейную интерполяцию компонентов u/v, температура — линейно. Это преобразование
самого прогноза; не замена на фактическую погоду. Покрытие исходных срезов обязательно.
Архив грубее Open-Meteo и требует существенно больше трафика (десятки МБ на выпуск).
Поэтому сначала проверять небольшой период и затем расширять обучение.
Источник: https://registry.opendata.aws/noaa-gfs-bdp-pds/

У модели зафиксированы источник и weather_model. Нельзя обучиться на Open-Meteo,
а при ошибке молча перейти на GFS: для другого источника нужно отдельное обучение.

## Запуск у коллеги

Python 3.12+, из корня репозитория:

```bash
python -m venv .venv
# macOS/Linux:
source .venv/bin/activate
python -m pip install -r backend/requirements-wind.txt
python -m backend.scripts.run_wind_hackathon --help
```

Рядом с корнем проекта передайте локальный `.env.wind`: в нём уже записано выданное
подключение к БД `wind`, HTTP-порт 8123. Файл исключён из git; передать отдельно.
Пароль не встроен в код и не выводится runner-ом. Используются `WIND_CLICKHOUSE_URL`,
`WIND_CLICKHOUSE_DATABASE`, `WIND_CLICKHOUSE_USERNAME`, `WIND_CLICKHOUSE_PASSWORD`,
`WIND_CLICKHOUSE_TIMEOUT_SECONDS`. Переменные окружения имеют приоритет над файлом.
Другой файл можно указать перед командой: `--env-file /path/to/.env.wind`.
На Mac, где опубликован Docker-порт, при необходимости заменить URL на
`http://localhost:8123`. Адрес <IP-хоста-ClickHouse> требует доступности локальной сети.

После создания/обновления схемы и импорта факта проверить подключение:

```bash
python -m backend.scripts.run_wind_hackathon check
```

Полный эксперимент через Open-Meteo, включая независимую проверку, обучение и
29 ежедневных запусков. Флаг ниже сознательно допускает неподтверждённые hindcasts;
для официального as-issued результата используйте операционный архив.

```bash
python -m backend.scripts.run_wind_hackathon workflow --source open-meteo --allow-hindcast --training-start 2025-10-01T18:00:00+05:00 --output-dir outputs/wind_forecast/open_meteo_experiment
```

Для операционного архива:

```bash
python -m pip install -r backend/requirements-wind-noaa.txt
python -m backend.scripts.run_wind_hackathon workflow --source noaa-gfs --training-start 2025-10-01T18:00:00+05:00 --output-dir outputs/wind_forecast/gfs_replay
```

Октябрь — стартовый объём для проверки и запуска. Можно расширить историю через
`--training-start`; у Open-Meteo Single Runs она начинается с 14.03.2024, поэтому
начальные факты 2023 года этим источником в обучение погодной модели не попадут.
По умолчанию workflow использует начало 15.03.2024.

`workflow` по умолчанию заканчивает обучение 31.01.2026 18:00 UTC+5, затем
выполняет origin до 28.02.2026 18:00 включительно, раз в сутки, горизонт 48 часов.
18:00 — выбранное время запуска, не условие организаторов. Точки первого окна
начинаются с origin. Факт после cutoff не читается финальной моделью.
Для отдельной проверки используется своя модель с cutoff за 30 дней до первого
тестового запуска; последующие 30 дней не используются ни для обучения, ни для
подбора её веса. Финальная модель затем переобучается на всём разрешённом периоде.

В выходном каталоге:

- `model.joblib`, `validation_model.joblib` — разные версии обученных моделей;
- `training_metrics.json` — метрики отрезка настройки финальной модели;
- `holdout_metrics.json`, `holdout.jsonl` — независимая проверка до теста;
- `replay.jsonl` — все 10-минутные и часовые прогнозы всех origin;
- `february_hourly_all_origins.csv` — все почасовые прогнозы, цели только в феврале;
- `february_hourly_latest.csv` — последний доступный origin для каждого часа;
- `workflow.json` — статус, происхождение погоды и проверка 1344 часов (2 × 28 × 24);
- `weather_progress.json` — ход загрузки;
- `replay/decisions.jsonl`, `replay/runs/*.json` — решения и результаты агента.

При повторном запуске исходные ответы берутся из кеша, уже обученные артефакты
используются повторно. Для изменения диапазона/настроек обучения задавать новый
выходной каталог. Для скорректированного ответа источника есть `--refresh` в
`fetch-weather`/`agent`; новая погода изменит хеш и приведёт к пересчёту.

Автоматическое наблюдение с зафиксированными виртуальными часами:

```bash
python -m backend.scripts.run_wind_hackathon agent --source open-meteo --allow-hindcast --artifact outputs/wind_forecast/open_meteo_experiment/model.joblib --origin 2026-02-15T18:00:00+05:00 --watch --refresh --poll-seconds 900
```

Без `--origin` в режиме `--watch` используется текущий час. Для остановки Ctrl+C;
для ограниченного числа циклов — `--cycles 3`. Один процесс на выходной каталог
защищён файловой блокировкой. При ошибке watch записывает причину и повторяет цикл
на следующем такте. Разовый запуск завершается ошибкой. При временной недоступности
источника агент может использовать сохранённый в ClickHouse подходящий выпуск,
но не подставляет фактическую погоду или будущий выпуск.

Проверки до публикации: полный горизонт обоих объектов, CF 0–1, согласованность
МВт и МВт·ч, почасовой средней мощности и интеграла 10-минуток. Изменения относительно
предыдущего прогноза вычисляются на пересечении часов; большие скачки отмечаются.
Новый вход создаёт новый `run_id`, одинаковый вход — прежний идентификатор без новой
публикации. При неполной записи в ClickHouse повтор восстанавливает тот же run_id;
читать результаты с `FINAL`. `--dry-run` в agent сохраняет погоду и отчёт, но не
публикует мощность в ClickHouse. Простой `predict --dry-run` только читает БД.

Агент реагирует на погоду, виртуальное время и загруженную версию модели. Новые
факты не изменяют уже зафиксированную модель автоматически: переобучение — отдельный
`train` с новым cutoff и артефактом. Факт февраля нужен для последующей оценки:

```bash
python -m backend.scripts.run_wind_hackathon evaluate --predictions outputs/wind_forecast/open_meteo_experiment/replay.jsonl
```

Без февральского факта команда возвращает `awaiting_actuals`. Метрики рассчитываются
по полным фактическим часам, отдельно 0–24 и 24–48 часов; каждый origin оценивается
отдельно. Нельзя суммировать обе детализации или разные версии прогноза.
Старые команды `train`, `predict`, `replay` сохранены для ручных этапов; сами они
не скачивают погоду. Для автономного полного запуска используйте `workflow`/`agent`.

## Допущения и ограничения

- CF = мощность / 2,5 МВт. Нормализация организаторами не подтверждена.
- Весь CSV трактуется в фиксированном UTC+5, включая 2023 год. Метка — начало
  10-минутного интервала. Средние ветер и температура не объявляются мгновенными.
- Мощность из CSV принимается средней за интервал для расчёта энергии.
- 80 м — опубликованная высота башни; точная высота измерителя неизвестна.
  При отсутствии прогнозного ветра 80 м используется 100 м без скрытого пересчёта
  по произвольно выбранному коэффициенту шероховатости.
- Объект сопоставлен с ВЭС Нурлы по координатам. Характеристики:
  https://samruk-green.kz/index.php/ru/projects/1047-20210219-133650
  https://www.thewindpower.net/windfarm_en_30769_nurly.php
- Измеренные `avg_wind`, `avg_tmp` сейчас служат для проверки/исследования факта,
  но не подаются как будущие признаки. Прямой ML-остаток учится на прогнозном ветре
  и тем самым учитывает систематические ошибки погодных прогнозов.
- TimesFM и коррекция по свежей мощности не используются: февральский факт не дан.
- Интерполяция погоды не создаёт новых наблюдений с 10-минутным разрешением.
- Диаметр 109 м — справочная характеристика, не постоянный ML-признак.
- Модель не знает статусы ремонта/диспетчерских ограничений, которых в CSV нет.
- Контроллер агента основан на явных правилах, без LLM: наблюдение → выбор инструмента/
  запасного выпуска → проверка → расчёт → анализ → публикация → повтор при изменении.
  Это автономный ML-процесс. Если жюри отдельно требует именно LLM tool-calling,
  такой дополнительной нормы в предоставленной постановке нет; LLM здесь не заявлен.
- API/дашборд не реализованы; результаты доступны в ClickHouse и CSV/JSONL.
- Отчёт прогнозирует работу при неизвестных будущих ремонтах/ограничениях; их факта нет.

## Проверка без БД

```bash
python -m unittest backend.tests.test_wind_hackathon backend.tests.test_wind_hackathon_agent -v
```

Проверяются подготовка, отсутствие будущих данных, агрегация, сопоставление
координат, кеширование, запрет неразрешённого hindcast, выбор старого полного выпуска,
пересчёт при изменении погоды, повтор после перезапуска и независимая оценка.
Полный синтетический workflow даёт 29 origin, 19 488 строк двух детализаций и
1344 уникальных февральских часа. Это проверка процесса, не реальной точности.

При подготовке комплекта успешно выполнен реальный запрос Open-Meteo для обеих
